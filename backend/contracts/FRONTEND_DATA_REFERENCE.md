# Frontend data reference: what the backend actually produces

This reconciles `whyledger_frontend_reference_full.csv` against what
`backend/finance_engine` + `backend/agent_engine` compute today.

**Status: the reference schema is now the real data model.** The backend
was refactored to run on `data/subscription_accounts.csv`, a synthetic
but realistic dataset generated by `data/generate_subscription_data.py`
matching the reference CSV's exact 112-column schema: one row per
customer account per active calendar month, with MRR lifecycle events
(new business, expansion, contraction, churn, SLA credits, refunds, usage
overage), product/support telemetry, and precomputed variance/driver/
historical fields. This is a genuine (if earlier) upgrade from the old
general-ledger dataset -- most of what was previously "not available" is
now real.

One structural note: the raw schema has no calendar column, only a
`month` integer. The engine treats it as a **global** index shared across
every account (so "month 10" means the same real calendar month for every
account) and converts it to a `"YYYY-MM"` period string anchored at
`2025-01` (`backend/finance_engine/ingestion.py: month_to_period`). An
account simply has no row before its signup month or after it churns.

## Two levels of variance, both real

- **Account-level** (`FinanceEngine.compare_periods` / `rank_variances`):
  one Variance per customer account, exactly mirroring the reference
  file's per-row MRR change. `breakdown_variance()` on an account variance
  splits it by billing-event category (New_ARR, Expansion, Contraction,
  Churn, SLA_Credit, Refund, Usage_Overage) -- the reference's
  `primary_driver_*`/`secondary_driver_*`/category-share fields.
- **Portfolio-level** (`FinanceEngine.get_portfolio_variance`): total MRR
  across every account. `breakdown_variance(dimension="account")` finds
  which customers actually drove it (the whale-vs-broad-based
  concentration story); `dimension="company_size"|"industry"|"contract_type"`
  gives the reference's segment rollups (`company_size_mrr_change`, etc).

## Available now

| Reference concept | Real equivalent |
|---|---|
| `current_mrr`, `previous_mrr`, `mrr_change`, `mrr_change_pct` | `Variance.current/previous/change/change_pct` |
| `variance_rank`, `material_variance_flag` | `VarianceCard.rank`, `.is_material` (from `rank_variances()`) |
| `new_arr_amount` ... `usage_overage_amount`, their shares | `Driver` list from `breakdown_variance()` on an account variance |
| `primary_transaction_type`/`primary_driver_amount`/`secondary_*` | `VarianceCard.primary_driver` / `.secondary_driver` |
| `largest_transaction_*` | `VarianceCard.top_transactions[0]` (`get_top_transactions()`) |
| `company_size_mrr_change`, `industry_contribution_pct`, `contract_type_*` | `breakdown_variance(portfolio_variance_id, dimension=...)` |
| `churn_flag`, `churn_reason_code` | present on every account row; a churned account shows `current_mrr == 0` and a `Churn` driver |
| `prior_3m_avg_change_pct`, `historical_change_label` | `VarianceCard.historical_trend`, `.change_vs_recent_avg_label` (`get_historical_account_changes()`) |
| `driver_summary`, `evidence_summary` | `VarianceCard.driver_summary`, `.evidence_summary` |
| A natural-language explanation | `VarianceCard.headline` / `.explanation` (Role 2) |
| A confirmed prior explanation surfacing again | `VarianceCard.confirmed_context` |
| Fact-checking a claim ("broad-based growth", "driven by X") | `NarrativeVerdict` (`verify_narrative_claim()`) -- including a concentration check for "broad-based"-style claims |

## Still not available (out of scope, not a bug)

- **`active_users`, `usage_growth`, `feature_adoption_rate`, `error_rate`,
  `tickets_count`, `payment_delay_flag`** and their `*_signal`/`*_driver_flag`
  columns: these exist in the raw CSV and are simulated realistically, but
  `FinanceEngine` does not currently read or expose them -- it is scoped to
  the financial/MRR columns per the hackathon's priority order (README
  section 24: correctness of financial numbers and drivers first). Wiring
  these in later is additive, not a rewrite -- they're already columns on
  `SubscriptionDataset.accounts_df`.
- **`next_month_mrr`**: a forecast. Explicitly a non-goal (README section 4).
- **`discount_pct`/`discount_change`, `regime_state`, `contract_type` as a
  pricing lever**: present in the data but not surfaced as a breakdown
  dimension beyond the segment rollup use above.

## Rule for the frontend build

Build against `VarianceCard` (`backend/contracts/frontend_view.py`) and
`build_dashboard()` (`backend/integration/dashboard.py`) -- run
`python3 -m backend.integration.demo_dashboard_export` for a real sample
JSON file. If a UI element needs a column from the "still not available"
list, it's a deliberate scope decision, not a backend gap to report.
